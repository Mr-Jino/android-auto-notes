# 用 AutoJs6 做 Android 自动化，我踩过的 5 个坑

> 写给我自己，也写给下一个想让手机自己干活的人。

## 缘起

我有个每天要重复点几十次的 App 流程，纯手工点，点完手指发麻。于是用 AutoJs6 写了个脚本替我点。

第一版跑得很顺，我甚至有点得意。然后它开始在三个地方栽跟头：按钮找到了但点不动、时长算对了但点早了、App 一更新整套逻辑报废。

前后改了五版，最后稳定跑通。下面这五条，是这五版换来的——**每一条都有日志、有复现、有具体数字**，不是"经验之谈"。

---

## 坑 1 · 无障碍树"看得到"，不等于"点得动"

第一版我用最标准的写法：

```js
const node = text("领取成功").findOne(2000);
node.click();          // 无障碍的标准点击，0ms 瞬时
```

日志显示：节点确实找到了，`click()` 返回 true，然后**什么也没发生**。

我以为是没找到，就加了循环连点。日志里是这样的：

```
[10-20 21:14:02] find 「领取成功」 -> click() -> true
[10-20 21:14:03] find 「领取成功」 -> click() -> true
... 连续 18 次，界面毫无反应
```

**连点 18 次，界面纹丝不动。** 那一刻我才意识到：`click()` 走的是无障碍点击，而有些控件——尤其是广告 SDK、游戏引擎、自绘的浮层——根本不走无障碍的点击通道。它们只认触摸事件（`MotionEvent`）。

解法是换成**带时长的按压**，让事件看起来像一根真手指：

```js
/** 自绘控件对 0ms 瞬时点击不响应，press 更接近真手指 */
function pressXY(x, y, ms, why) {
    press(x, y, ms);           // 带时长，通常是 100~150ms
    log(`press(${x},${y},${ms}ms) ${why || ""}`);
}
```

`press(x, y, 120)` 之后，一次就点中了。

> **教训**：`click()` 返回 true 只代表"无障碍服务接受了这个请求"，不代表控件处理了它。**返回值和实际效果是两件事**——这在自动化里是通用的陷阱，不只是安卓。

## 坑 2 · 写死的时长，一定会算错

广告/加载类页面有个共同点：你无法从无障碍树读到"还差几秒"。第一版我干脆写死等 35 秒再去点领取。

跑了一周，翻了两次车：

- 有时广告 40 秒，我在第 35 秒点了右上角的"×"，直接跳过，弹窗「再看 N 秒继续解锁」，脚本又去点那个位置——**死循环**
- 有时广告 25 秒就播完，我等满 35 秒才点，白等 10 秒

我把"等待"改成了**状态机**：

```js
// 能读到倒计时 -> 一直等它消失
// 读不到 -> 按 35s 兜底，但每 1.2s 检查一次「继续观看」弹窗，见到就点
const resume = pick(nodes, ["继续观看"]);
if (resume) tap(resume);      // 误触退出后的救回
```

关键不是把 35 秒调成 40 秒——**任何写死的时长都会在某个版本失效**。关键是把"等"变成一个可被新信息打断的循环。

> **教训**：自动化的健壮性来自"每一轮重新判断状态"，不是来自"把参数调准"。

## 坑 3 · 只有一条路径的脚本，只能在一个版本上活

这个 App 有意思的地方在于：它的不同页面，自动化能力完全不同。

- 播放页：无障碍树能读到文字（"免费听"）→ **按文字点**，最稳
- 广告页：SDK 自绘，文字读不到，但布局稳定 → **按坐标 + 按压**
- 全屏浮层：连播放页文字都读不到 → 整套退化成**定时点击**

所以我最后写的是**三模降级**，脚本自己判断该走哪一层：

```
能读到文字 → 文字模式（最稳，抗改版）
   ↓ 读不到
能读到倒计时 → 计时模式（等它走完）
   ↓ 读不到
什么都读不到 → 坐标模式（最脆，但能跑）
```

写降级链的代价是要维护三套逻辑；不写的代价是 App 一更新脚本就死。我选了前者，因为**改版是必然的，不是意外**。

> **教训**：自动化脚本的寿命，等于它有几条退路。

## 坑 4 · 自动化必须能被随时掐断

这个坑不是技术坑，是"给自己留后路"的坑。

脚本在后台跑的时候，我有时候需要立刻停下来——它点到了不该点的东西、或者我想用手机了。最初的版本只能靠"切到 AutoJs6 界面按停止"，这在你手上正忙着别的事时几乎不可能做到。

现在有两个开关：

1. **悬浮窗「停止」按钮**——看得见，点得到
2. **信号文件**：`/sdcard/qishui_STOP`，主循环每轮检查一次

```js
if (files.exists(STOP_PATH)) {
    log(">> 检测到停止信号，退出。");
    try { files.remove(STOP_PATH); } catch (e) {}
    exit();
}
```

为什么还要文件信号？因为它**不需要和 UI 交互**——你可以用任何方式创建这个文件（另一台设备、电脑 adb push、甚至同步盘的脚本），脚本在下一轮轮询时就会退出。悬浮窗按钮依赖 UI 存活，文件信号不依赖。

> **教训**：任何"会自己动你的设备"的程序，都得留一个**不依赖它自己 UI** 的停止通道。这条比任何功能都重要。

## 坑 5 · 日志比猜测便宜一百倍

前面几个坑能定位，靠的全是日志，而不是我"再想想哪里不对"。

最有用的一条设计是**失败自证**：同一个按钮连点 3 次没反应，就换标定点再试；第 5 次还不行，直接把当前屏幕的完整节点树 dump 到日志里。

```js
if (attempt >= 5) dumpAllNodes();   // 别再猜了，把现场留下来
```

事后翻日志，一眼就能看出"我以为的按钮"和"实际的按钮"差在哪。如果没有这一步，我大概率会去改一个根本没问题的参数。

> **教训**：自动化的调试成本，取决于你留下了多少现场。**失败时把状态全打出来，比成功时打日志重要得多**。

---

## 附 · 别在坏的工具链上硬修

一句题外话，但我觉得比上面五条都值钱。

我一开始走的是电脑端方案：电脑通过 adb 连手机，截图、识别、再用 adb 点击。折腾了两个晚上，最后确认——**这台机器的 USB adb 就是坏的**（驱动、线、端口全排查过）。

我当时的反应是继续修 adb。正确的做法是：**换通道**。文件传输模式（MTP）拖拽，一样能把脚本放进手机，而且不用装任何东西。

我把它写进说明文档的第一行，还加了句「别再修 adb」，就是怕未来的自己又钻回去。

> **教训**：判断"这条路坏了"比"把这条路修好"更省时间。修之前先问一句：**换个通道要几分钟？**

---

## 最后：关于边界

这套东西我只用来替我点**我自己本来就会点的操作**——省的是手指，不是占谁便宜。

有两件事我没做，也不建议做：

- **不用它去伪造曝光、刷量、模拟真人看广告**。这不是"技术中性"，这是替别人浪费广告主的钱，平台封号是迟早的，而且这类脚本一旦公开，评论区不会聊技术，只会问"能不能帮我代跑"
- **不把它做成"服务"**。一旦有人拿它收费，性质就彻底变了

技术本身没什么可羞耻的，但**自动化把人的动作复制了一万次，代价会放大一万倍**。这条线画在哪儿，得自己心里有数。
